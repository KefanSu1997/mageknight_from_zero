# 完整 Demo 初版与连续战斗集中验收

用户通过已配对飞书提出：先把所有要素做初版放到战斗Demo，再设计战斗流程，一次游戏覆盖大量测试。开发顺序据此调整，不再默认逐一两项接入后即做完整独立场景批次。

## 已确认的慢点与基线

- 当前有61个出战快照、13种遭遇，通过循环按钮选择。上一批首次179步中58步仅用于抵达出战配置；补最后一个双部队场景82步中60步是选配置，不应把这种操作数量当作测试效率。
- `PveBattleController.Begin`每次调用`Loadout.CreatePlayer`重新生成玩家。当前“再战”是另一个初始快照，不是保留状态的连续游戏；无法顺便验证真实卡区、部队创伤、耗竭、技能次数跨战斗的期限。
- PVE当前仅直接映射4种原行动卡，19/30部队、10/25神器、17/70自身技能有有限场景证据。原卡121/121有限基本验收的历史证据独立保留，不重复全测。

## 新交付顺序

1. 全量原要素接入初版。以原定义、素材、正式效果为来源，补合法输入、目标、费用、使用时机和消费者；行动/高级行动/法术沿用既有正式实现，神器25、部队30、各英雄自身技能共70统一纳入。一览和直接选择代替循环61个测试预设；只有真实可操作才记已接入，未支持清楚保留缺口。
2. 可持续的一局流程。准备英雄/合法构筑 → 选择遭遇 → 正式远程/格挡/承伤/近战 → 战后恢复与奖励 → 正式结束回合、补牌 → 下一场；需要重整每轮资源时走正式新轮入口。连续持有同一玩家/原牌实例与正式上下文，不重置伤牌、魔力、声誉、单位状态或已用技能。招募、探索等非战斗效果放入相应正式阶段，不硬塞战斗按钮。
3. 按英雄和构筑编排验收路线。路线依次消费原攻击/格挡、各元素/抗性、承伤/治疗、魔力来源/印刷费用、部队与神器、技能次数，覆盖结果和后续影响。英雄自己的技能、有限指挥槽及互斥选择要求多组路线；不承诺一局覆盖全部内容，也不造超出规则的全技能角色。
4. 集中验收与失败定位。先成批跑新增/受影响的真实后台状态检查，再启动一次Unity执行多场连续路线。每个操作记录来源ID、模式、合法选择、费用、实际前后值和断言；关键阶段/复杂交互截图，不逐点击截图。对已通过区间保存可重放检查点和版本依赖，失败仅补对应区间。检查点必须保留实体身份、牌序、随机状态、资源及期限，不能只是重新注入目标数值。

## 完成口径与风险处理

- 接入初版、后台通过、场景通过分列；初版不是验收完成。
- 仍检查原图/原文/实际效果一致，后台失败先修再走场景；不降低最终场景验收标准。
- 首个连续流程烟测须验证同一玩家真实跨两场、一次回合结束与新轮边界，避免把旧Reset包装成Continue。完整要素铺开期间不为每项单独制造新快照。
- 依赖正式`GameEngine`/`TurnManager`/`TurnMachine`/`CardPlayActions`/`CardUnitActions`/`SkillActions`，不另写简化规则引擎。`PveBattleSession`负责战斗，回合/招募/地图仍由对应正式服务承担。
- 现有技能`Frequency.Unspecified`或部队loader拒绝的情况属于真实接入缺口，不能放开校验、猜测频率/选项或只展示素材来凑数量。
- 本次完成流程设计与项目约定更新，尚未实现全量初版或连续战斗控制器，不增加通过数。不因计划文档变更启动Unity或后台回归。
