# 基础 Demo 流畅度：实际指标基线

用户要求明确计算方式、测当前基础版本的数值，并提供与个人体验对比的材料。本轮仅增加显式启用的测试计时，不改变UI布局、游戏规则或PPO奖励，没有训练更新。

主报告：AutomationOutputs/UiFluency/20261012_baseline/baseline_report.md；完整计算结果metrics.json；actual_ready/trial_00—02保存请求、实际点击、前后状态和截图。

## 测试和计算

真实Unity 6000.6.0f1、1920×1080 Game View，通过原Tovak16牌/战术/回合/开战入口建立局面。每组同一实际会话用原Demo阶段检查点重打，保持该组两条攻击路径的牌序和状态；不同组的抽牌不强行冒称配对随机流。组内短/显式攻击的共享正式快照，操作前后全部相等（6项比较通过）。

测3组×6正常意图=18任务，18/18完成。另3个预期“攻击不足”拒绝探测正确拒绝，不混进普通误操作率。57个任务内实际指针点击，3078共享字段前后对照通过。设置与造局点击单列，不算任务内操作，也不是PPO覆盖。

## 关键实例与优化方向

1. 全用攻击已有2点击路径，显式路径5点击/2面板切换；两者共享规则结果相同。截图中当前已显示有效攻击/护甲和不足2提示，说明基础预览已具备。文案“选择本次攻击来源”可能让玩家以为必须进分配面板，此为可发现性假设，需本人体验确认。优先明确默认全用和可选分配，不删除子集控制。
2. 横置操作横跨左侧手牌与右侧按钮；恢复操作6625px的往返最多。可试就近按钮、上下文菜单或快捷键，再比较同一意图。当前尚未实施。
3. 选新牌清空目标是实际行为，而不是猜测。可以考虑独立保留兼容的攻击意图目标，或明确旧选择何时失效；不能不经规则检查保留所有付款/材料/目标。
4. 承伤提交三次首帧184.62/871.32/280.62ms，handler中位264.21ms。同步处理已有耗时，下一步应分段测Advance、阶段检查点Capture和Draw，不能先把原因归为动画。代码Act每次调用Draw，Draw会重建BattleTable；其性能影响需要Profiler验证。

不同任务内每次点击延迟的P50/P95见主报告。单任务只有3重复，小样本不作用户人群推断。该环境为编辑器，同机其他训练/应用未停止；一次观测空闲物理内存约800MiB，可能有负载影响，不能外推出发行版性能。

历史弱策略诊断单列：7旧episode共171点击，27次观察无变化代理（15.8%）、50次重访代理（29.2%）、4次规则拒绝。不同旧UI/策略版本，不能当当前UI或普通玩家错误率；目前脚本18意图完成也不证明策略已有流畅能力。

## 启动异常与证据完整性

第一次入Play观察90s超时，无任务记录，actual/trial_00原样保留。第二批前2组完成后第3组菜单transport超时，实际菜单后续已执行；refresh恢复并确认当前会话目录后attach_pending，仅从尚未发请求的第3组继续，未重跑前2组。attachment.json与原launch失败都保留。

Console在结束后发现Unity PlayMode内部Assert：DefaultScenario was Idle but expected Starting。保存console_final_1/2.json，不宣称该生命周期问题已修复。它未出现在57任务点击的运行期记录中，任务pointer成功、断言和共享状态对照均通过。隔离历史日志、refresh后console_current_1/2.json两读0；这是当前Console状态，不是发动过的旧Assert不存在或整个Demo全验收。

新增计时在StructuredUiPilot请求measure=true时启用；默认旧请求不计时。规则/UI业务代码未改。Python分析先出现括号错误，修复后py_compile与实际数据分析通过。公式/原始JSON/源码与DLL签名可查；分析不伪补真人评分或旧时间戳。

## 用户体验对照

主报告有“你的体验”列和实际截图。建议本人在类似局面尝试：横置一张牌、全用攻击直接结算、打开分配来源、故意攻击不足后补两张牌重攻、确认承伤。对照鼠标往返、默认行为是否清楚、目标是否要重选、是否明显停顿。体验差异可以指向下一轮任务和埋点，而不是用自动分数压过实际感受。
