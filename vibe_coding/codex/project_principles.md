# MageKnight｜开发原则与执行约定

版本：2026-09-15。适用范围：整个 MageKnight_from_zero 项目，包括规则代码、美术、场景、测试、demo、文档和远端同步。来源：用户明确要求与项目 AGENTS.md；后续开发必须执行。

## 1. 最小必要原则

以完整达成目标为前提，只做必要修改、必要验证、必要记录和必要传输。不能以减少工作为由降低标准、缩小用户目标、删除失败用例或隐藏未完成范围。

- 修改前先查现有实现、原版定义和原素材。围绕当前问题作最小充分修改，不顺带重构或引入新框架。
- 日常验证只执行新增、失败、修改和直接受影响的用例。已通过用例退出日常队列，保留在回归库及历史证据中。
- 修改共享规则时，按实际影响选取回归；确实涉及广泛影响、已有回归失败或阶段验收需要，才扩大范围，并记录原因。
- 不因现有入口按整批组织，就反复重跑两百多张卡或整个卡库。无新修改、失败或未解决疑点，不重复已通过检查。
- 用精简摘要、路径和哈希索引保存证据。只保留有验收价值的截图，避免重复截图、大日志反复读取和无依据的网络重试。

## 2. 延展性原则

当前任务、测试与 demo 必须能为最终成品游戏服务或有用。阶段展示应积累可复用内容与能力。

- 卡牌：既有原版定义、卡面和效果同源；实例与牌区、支付与结算必须连接真实规则。除非用户要求新卡，禁止 DIY 卡牌或猜测数值。
- 内容：怪物、英雄、部队、地点和场景美术分别作为可引用资产；场景用内容定义搭建，不把“剑士 VS 兽人”等演示写成只能运行一次的特殊逻辑。
- 规则：移动、探索、交涉、招募、战斗、伤牌、魔力、回合/轮次等实现供正式玩法和测试共同使用。
- 操作：采用用户选定的“卡牌与目标驱动，规则按需展开”。玩家通过选卡/部队、选目标、确认行动完成玩法；数值加减器、案例切换收进调试入口。
- 测试：通过真实场景与操作连接规则和数值。保留可重放用例；不以直接改状态、假结算或一次性按钮演示替代正式效果验证。
- 验收前回答：这项工作给成品保留了什么资产、能力或可重复证据？哪些部分仍只是验证入口，尚未接入完整游戏？

## 3. LFS 与传输原则

只有美术资产需要 Git LFS 同步。不能把“文件很大”或“扩展名是 PNG”当作美术资产的判断依据。

用户特别澄清：这条约定的重点是禁止把测试截图作为 LFS 上传，避免再次耗尽 VPN 流量；不能把它曲解成需要额外整理或上传测试证据。

- 原卡面、角色/怪物/地点素材、模型、材质依赖纹理等正式美术内容：按需使用 LFS。
- 代码、规则设计、配置、资产索引、JSON 预期、文本验收摘要：普通 Git。
- 测试截图、运行录像、Unity 日志、完整轨迹、缓存和中间报告：默认本地保存，通过路径和哈希索引引用，不自动上传。
- 声音、视频等其他大文件若新增同步需求，先明确其用途，不自动扩展“美术资产”范围。
- 远端推送目前暂停。后续传输先列必要内容、对象数和体积，再执行已获授权的同步；不修改 VPN 设置，不重写历史或强制推送。
- 旧历史里已存在的 LFS 验收图片不代表今后继续这样做；历史清理或迁移另行确定范围。

## 4. 规则和设计的优先顺序

1. 用户明确的项目范围、操作偏好和原则。
2. 原版规则书、对应原卡面和明确适用的规则特例。
3. 核对过的项目规则设计及可追溯实现。
4. 旧笔记、旧 demo、历史代码仅作为线索；发生冲突必须回到规则原文，不照抄错误摘要。

所有规则修改都要说明：原条文/卡面是什么，当前行为哪里不同，修改后怎样，实际操作和数值如何证明。未覆盖项明确记录；不以当前运行结果反推测试预期。

## 5. 规则—进度—验证三位一体

每条开发记录至少包含：规则编号或卡牌 ID、来源/页码、实现位置、当前进度、测试场景和操作、独立预期、实际结果、证据路径、剩余边界。

- “已有实现”：存在代码或数据，尚不能据此认定正确。
- “单元验证通过”：逻辑用例通过，不等于真实场景与视觉验收通过。
- “已测分支通过”：已列出的操作链和数值符合预期，仍可能有未覆盖分支。
- “待联验/partial”：即时断言通过，但后续规则、期限、费用、目标或消费链尚未完整验证。
- “失败”：保留明确不符的断言和原预期，进入修复队列。
- “完整通过”：约定范围的来源、卡面、操作、费用、实际结算、失败守恒、后续行为与期限均有足够证据。

## 6. Unity 与工作记录

- 当前编辑器为 Unity 6000.6.0f1，通过 Unity Hub 打开。禁止 batchmode 或命令行直接启动 Unity.exe；禁止安装、卸载 Unity packages。
- 游戏代码修改后，按 AGENTS.md 从 Unity Console 拉取 error，取得两次零错误；不能用外部语法检查代替。
- 场景修改要实际运行受影响的自动化场景，检查操作命中、数值/规则对应及必要截图。纯文档/记忆变更不启动 Unity 测试。
- 工作记录写入 vibe_coding/codex；新的经验记录到 project_experience 并更新 AGENTS.md 索引。
- 保留用户其他未提交修改。提交前展示 diff，提交保持小而完整；不向 main 直接提交，不强制推送。

## 7. 当前阶段的执行顺序

先完成可追溯的规则与进度资料，再恢复原版卡牌效果验证。以未完成的魅惑交涉/招募链为起点，继续失败、缺失和 partial 分支；已通过范围退出日常执行队列。更大范围的部队、技能与完整剧本整合保持显式待办，不冒充已完成。
