# 战斗PPO真实状态闭环

- 扩展到真实起始牌库后必须接入普通源骰，否则训练会系统性缺少强化费用；使用正式 `CardManaActions.UseSourceDie`，金色在付款时转换。全伤手牌的最低活动门禁须保留并记录轨迹停止原因，不能用强制补牌掩盖合法入口缺口。连续三回合不等于跨三轮。扩展工作记录：`vibe_coding/codex/worklog_2026-10-01_persistent_ppo_training.md`。

用户再次纠正后，正式目标是全部英雄/战斗/原卡在训练实际使用，并跨多回合和昼夜轮次；固定家族胜率不得用作完整目标的算力结论。覆盖清单导出时法术原名来自 `spell_top.name`，不是行动卡的 `card_name`；首次漏掉24法术已修正，不能把数据字段差异当作该类别不存在。完整契约见 `vibe_coding/codex/combat_ppo_full_scope_2026-10-01.md`。

- 训练直接复用正式逻辑：状态向量、动作掩码和UI按钮映射有独立版本与明确声明范围；不另写护甲、费用或卡牌模拟器。
- 掩码预执行必须原子恢复真实资源与实体，模型在实际step仍二次校验；未知范围拒绝，不拿少数特征缓存全游戏合法性。
- PPO评估必须使用独立环境进程，不能重置正在收集的rollout。此错误会使观察和实际状态断裂，即使梯度实现正确也无效。
- 从保存且重新载入的模型生成实际UI动作；逐操作核对原规则状态与场景数值，不用脚写赢家或直接注入状态冒充RL闭环。
- 少量固定场景的200个seed不是200种构筑。展示初版成功时同时记录随机基线、未训练基线、测试集变动维度与覆盖缺口。
- 小向量PPO首先测环境采样与网络更新分项。此轮采样22.3秒、更新1.4秒，CPU吞吐1121步/秒；增加GPU不能替代合法动作/状态工程，温缓存吞吐不能直接当全卡库速度。
- RL可能利用共享规则bug，赢了不是正确性证明；仍需原卡独立预期、不变量与最终场景门禁。

代码与证据路径：`vibe_coding/codex/worklog_2026-10-01_combat_rl_ppo_pilot.md`、`tools/BattleRl/README.md`。
