# 飞书图片须独立持久队列并验证实际转交

旧接收器只接受text/post，单独image被直接忽略，post中的img也未提取。不能用文字收发成功推断图片可用。

新增media_pending队列与独立下载线程：配对身份及私聊校验后，消息和图片引用在同一SQLite事务入库；按消息ID去重，文件名使用消息ID与资源key哈希，不使用用户提供路径。单条最多4张，每张10MiB，识别PNG/JPEG/GIF/WebP/BMP；失败退避并明确回复，取消中的下载不能恢复已取消指令。只有下载完成才转交绝对路径；附带文字明确图片内容不是自动执行的指令。

6项图片测试和12项受影响桥接测试通过。22:41原用户照片经真实Feishu图片API下载640738字节，media状态进入attached、重试0；当前任务收到补充指示并通过view_image实际看到同一黑屏照片，形成下载—持久队列—桌面转交—读取完整证据。文件留在用户运行目录incoming，不上传Git。

部署时曾出现子进程初始化未完成，被90秒启动宽限后的旧心跳检查回收；具体根因尚未确定，不能记成已修复。补充不含凭证的启动阶段日志，随后一次SDK导入26.3秒并完成队列初始化，健康检查在线。服务启动/进程存在不能替代当前实例心跳和真实消息验证。

针对初始化被过早回收，守护器改为首次当前实例心跳前最多等待300秒，超时记startup_timeout；已有心跳后继续检查180秒过期、线程退出、传输离线。6项恢复回归通过，守护服务重载后7.8秒初始化成功、当前实例在线、历史补收成功，已attached图片保持且没有重派。冷开机验证与初始化慢的底层原因仍未确认，不以这次服务重启冒充整机重启验收。
