# 原版英雄技能：来源身份与使用次数（2026-09-10）

## 问题与修复

原始数据有8个英雄池、82条技能，另有32条部队。这些记录不在既有125条行动/法术/宝物统计之内。已有技能效果类不等于已接入完整技能系统：原加载器统一标记可重复使用，既不保留使用频率也没有统一所有权入口。

SkillCard 追加来源编号（英雄池+池内索引）、原文、频率，保留旧构造参数。SkillActions 必须验证实际持有对象，不能让同名但并非持有的对象执行任意效果。次数标记放在 PlayerState，通过来源编号索引；从供应区重新载入同一原技能仍不能刷新次数。每回合、每轮标记由正式生命周期入口分别恢复。

不要用 JSON 的 flip 字段推断每轮次数：暗火魔法的 flip=false 仍明确写着“每轮一次，将本标记翻面”。该字段也用于表示资料中的双面技能，应以原文的频率契约为准。没有明确契约的复杂技能保持未接入状态，不能默认无限激活。

首批五技能在执行前验证选项。燃烧之力必须产生攻城物理/火焰1，炽热剑术必须产生物理/火焰近战2；不能只改总值而丢失攻击方式或元素。

## 场景证据

原始 `Assets/GameData/cards/skill_000.png` 是一整张技能表，场景原样展示，显示当前技能的原文及逐步实际值/预期值。39个独立案例覆盖240次真实按钮操作、1614条断言、164张截图。包括技能取得、重复使用拒绝、重新载入、换回合、换轮、选项非法、未持有，以及移动费用和实际抗性战斗结算。

首次运行被 SHA256 断言拦截：Windows Python write_text 默认换成 CRLF，而 Unity 对文本规范化 LF。修正生成器显式 newline='\n'，保留版本检查；没有改动任何效果预期。首次通过运行 `AutomationOutputs/HeroSkills/20260910_231918_73e292b6`；清理生成场景及meta行末空格后，再次验证的最终运行 `AutomationOutputs/HeroSkills/20260910_232750_4614deb3`。

Unity JsonUtility 回写请求时会补齐 before/after=[]、skipScreenshot=false、waitAfterSeconds=-1。配置比对应只规范化这些明确默认值，同时完整比较每条操作和断言，不能直接取消请求一致性检查。

## 边界

这些用例证明的是首批五技能的入口与列出的分支，不能据此把82条技能或32条部队标记为通过。多人当前行动权、其它复杂技能的时机/立即支付/目标、完整冒险界面、影响力消费等仍待联验。原有490例单独回归，统计不得混在一起。
